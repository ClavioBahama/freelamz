Resumo

FreelaMZ — plataforma de contratação de freelancers em Moçambique

Este relatório descreve o desenvolvimento e a implantação do FreelaMZ, uma plataforma digital que liga clientes a profissionais independentes (freelancers) em Moçambique. O ponto de partida foi um problema concreto: existe muito talento no país, mas a contratação acontece sobretudo por indicação ou em grupos de mensagens, sem histórico, reputação nem registo do acordo.

A solução foi construída como uma aplicação web progressiva com aspeto de aplicação nativa, empacotada para Android, suportada por uma API REST e uma base de dados relacional. A plataforma cobre o percurso completo de um trabalho: publicação de serviços, envio e aceitação de propostas, gestão de projetos, mensagens, carteira com mecanismo de garantia (escrow), avaliações e notificações.

O sistema foi publicado em ambiente de nuvem, com base de dados gerida, e o pacote Android é gerado automaticamente por integração contínua. Os resultados incluem uma API pública funcional, 130 verificações automáticas aprovadas e uma aplicação instalável. O relatório documenta ainda as dificuldades encontradas, as decisões técnicas tomadas e o trabalho futuro necessário para transformar o protótipo num produto em produção.

Palavras-chave: marketplace; freelancers; Moçambique; React; Node.js; MySQL; API REST; Android; integração contínua.

Capítulo 1

1. Introdução

1.1 Contexto

A economia digital moçambicana tem crescido e com ela a procura de serviços especializados: criação de sites, design gráfico, gestão de redes sociais, fotografia, redação, contabilidade e desenvolvimento de aplicações. Em paralelo, muitos jovens adquiriram competências técnicas e trabalham de forma independente.

Apesar disso, o encontro entre quem oferece e quem procura esses serviços continua a depender de canais informais. O resultado é um mercado pouco transparente, onde o preço varia sem critério, o prazo raramente é registado e a qualidade não é comparável.

1.2 Problema

O problema pode ser resumido em três pontos:

  1. Procura dispersa. O cliente não tem um lugar único onde encontrar e comparar profissionais.
  2. Ausência de reputação. Não existe histórico público de trabalhos concluídos nem avaliações verificáveis.
  3. Acordos informais. Preço, prazo e entrega são combinados em conversas privadas, sem qualquer registo.

1.3 Objetivos

Objetivo geral: conceber, desenvolver e publicar uma plataforma que organize a contratação de freelancers em Moçambique, do primeiro contacto ao pagamento.

Objetivos específicos:

  • Modelar os perfis de cliente, freelancer e administrador, com permissões distintas.
  • Implementar o fluxo completo: serviço → proposta → projeto → entrega → avaliação.
  • Disponibilizar uma API REST documentada e uma aplicação Android instalável.
  • Publicar o sistema em nuvem, com base de dados gerida e implantação automatizada.
  • Validar o funcionamento com testes automáticos e utilização real num telemóvel.

1.4 Justificação

A plataforma reduz o custo de procura para o cliente, dá visibilidade ao freelancer e cria confiança através de reputação e registo. Para além do valor imediato, o projeto serve como estudo aplicado de arquitetura cliente-servidor, autenticação, modelação de dados e implantação contínua — competências centrais na engenharia de software atual.

  • Disponibilidade: o serviço mantém-se online mesmo com a base de dados temporariamente indisponível.
  • Portabilidade: a mesma API serve a aplicação Android, o site e os testes automatizados.

3.3 Modelo de dados

A base de dados tem 15 tabelas. As principais são users (contas), profiles (perfil profissional), categories e skills (catálogo), services (oferta), proposals (negociação), projects (execução), messages (comunicação), reviews (reputação) e wallets (saldo e escrow).

As chaves estrangeiras garantem integridade referencial com remoção em cascata onde faz sentido, e existem índices nas colunas mais consultadas (estado do projeto, destinatário da mensagem, categoria do serviço).

4.2 Decisões técnicas

Uma API para todos os clientes

Em vez de lógica duplicada, a aplicação Android, o site e os testes consomem os mesmos endpoints. Isso reduz inconsistências e permite testar as regras de negócio diretamente, sem interface.

Segredos apenas em variáveis de ambiente

Nenhuma credencial é escrita no código. Em desenvolvimento usa-se um ficheiro .env local (ignorado pelo Git); em produção, as variáveis são definidas no painel do Railway. Os erros de configuração listam apenas os nomes das variáveis em falta.

Operações idempotentes

Tanto a criação do esquema como o povoamento com dados de demonstração podem ser repetidos sem duplicar registos. Isso torna a implantação segura e previsível.

4.3 Controlo de versões

O código está num repositório Git privado, com uma ramificação principal (main). Cada alteração relevante foi registada num commit descritivo, o que permite reconstruir a evolução do projeto e rever decisões.

Capítulo 5

5. Implantação e publicação

5.1 Backend

O servidor está publicado no Railway. O serviço usa a pasta backend como raiz, o construtor RAILPACK e o comando npm start. O health check aponta para /api/health, com tolerância de 120 segundos, e a política de reinício é “em falha”, com até 10 tentativas.

Endereço público

https://freelamz-production-7103b885.up.railway.app/api

5.3 Base de dados

A base de dados MySQL é gerida pelo Railway e reside no mesmo projeto, com ligação interna. A inicialização aplica, por esta ordem: esquema, catálogo (categorias e competências), migrações e criação do administrador. O povoamento com dados de demonstração é opcional e idempotente.

5.4 Aplicação Android

O APK é produzido pelo GitHub Actions em quatro passos: compilação do frontend com a URL da API, sincronização com o Capacitor, compilação com Gradle (Java 21) e publicação do artefacto. O processo demora entre dois e quatro minutos e dispensa a instalação do Android Studio.

Resultado

Três versões do APK foram geradas com sucesso durante o desenvolvimento, incluindo a versão final que integra a página “Sobre” e o login corrigido para telemóvel.

Capítulo 7

7. Dificuldades encontradas e soluções

O desenvolvimento em ambiente real expôs problemas que não aparecem num servidor local. A Tabela 7 documenta os principais, a causa identificada e a correção aplicada.

Tabela 7 — Problemas, causas e soluções
SintomaCausaSolução
Deploy em ciclo de reinícios Base de dados ainda a inicializar Arranque resiliente, retentativas e health check sempre disponível.
Configuração da base de dados incompleta Variáveis com nomes diferentes no fornecedor Prioridade a MYSQL_URL e alternativas para a palavra-passe.
Aplicação vazia em produção Apenas catálogo e administrador Seed de demonstração idempotente.
Dados não chegavam ao servidor URL da base de dados vazia na máquina local Criação automática no arranque, usando a ligação interna.
Login cortado no telemóvel Altura fixa e falta de margens de segurança CSS com centragem real, suporte a notch e campos de 16 px.
Página inicial exigia sessão Endpoints privados e resposta 401 a encerrar sessão Perfis públicos e encerramento apenas quando existe token.
Caracteres acentuados corrompidos Codificação do terminal durante os testes Testes passaram a usar scripts em Node.js com UTF-8.
Lição aprendida

A maior parte dos incidentes não estava no código da aplicação, mas na configuração do ambiente. Validar cedo as variáveis e expor diagnósticos claros (sem revelar segredos) poupa horas de depuração.

Capítulo 8

8. Segurança e privacidade

8.1 Autenticação e autorização

As palavras-passe são armazenadas com hash bcrypt, nunca em texto simples. Após o login, o servidor emite um token JWT assinado, com prazo de validade. Cada pedido protegido valida a assinatura e o tipo de utilizador, impedindo que um cliente execute ações de administrador.

8.2 Exposição de dados

Os perfis de freelancers são públicos para permitir explorar a plataforma sem conta. No entanto, as respostas públicas omitem o email e os métodos de recebimento, que permanecem visíveis apenas para o próprio utilizador e para o administrador.

8.3 Gestão de segredos

  • Credenciais apenas em variáveis de ambiente, nunca no repositório.
  • Ficheiro .env local excluído pelo Git.
  • Mensagens de erro mostram nomes de variáveis, não valores.

8.4 Comunicação e validação

Todo o tráfego em produção usa HTTPS. O CORS está limitado às origens da aplicação e do site. Os uploads têm limite de tamanho e validação de tipo, e as consultas à base de dados usam parâmetros, prevenindo injeção de SQL.

Capítulo 9

9. Limitações e trabalho futuro

9.1 Limitações atuais

  • Ficheiros efémeros: o disco da nuvem é reiniciado a cada implantação; sem volume persistente, as imagens perdem-se.
  • APK de desenvolvimento: o pacote não está assinado para publicação na Play Store.
  • Pagamentos simulados: o modo de teste não movimenta dinheiro real.
  • Sem notificações push: os avisos existem apenas dentro da aplicação.
  • Contas de demonstração com palavra-passe pública: adequadas a testes, não a produção.

9.2 Trabalho futuro

  1. Configurar volume persistente ou serviço externo de imagens (por exemplo, Cloudinary).
  2. Integrar pagamentos reais de M-Pesa e e-Mola em ambiente de testes.
  3. Assinar o pacote Android (AAB) e publicar na Play Store.
  4. Implementar notificações push com Firebase Cloud Messaging.
  5. Alargar os testes end-to-end e automatizar a verificação da interface.
  6. Adicionar painel de métricas para o administrador.

Capítulo 10

10. Conclusão

O FreelaMZ partiu de um problema identificável — a ausência de um espaço organizado para contratar freelancers em Moçambique — e chegou a uma aplicação publicada, com base de dados, API e pacote Android. O percurso cumpriu os objetivos definidos: o fluxo de trabalho está implementado de ponta a ponta, os perfis e serviços estão acessíveis, e a implantação é reproduzível.

O trabalho confirmou que a complexidade de um projeto real não está apenas na escrita do código, mas na configuração do ambiente, na validação contínua e na capacidade de diagnosticar falhas com informação limitada. A existência de testes automáticos, de um health check informativo e de operações idempotentes revelou-se decisiva.

Como trabalho futuro, a prioridade é consolidar a infraestrutura (armazenamento persistente e pagamentos reais), assinar a aplicação e preparar o lançamento. O protótipo está pronto para evoluir para um produto utilizado por clientes e freelancers reais.

B.3 Reprodução do ambiente

  2. Clonar o repositório e instalar dependências em backend e frontend.
  3. Configurar o ficheiro backend/.env com as variáveis da base de dados.
  4. Executar npm run db:init e, opcionalmente, npm run db:demo.
  5. Iniciar a API e o frontend e abrir a aplicação no navegador.
  6. Para o APK, configurar a variável VITE_API_URL no GitHub e executar o fluxo “Build APK”.
