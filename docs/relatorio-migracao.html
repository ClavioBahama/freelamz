Resumo

Migração do FreelaMZ para hospedagem gratuita

Este documento regista a migração da infraestrutura do FreelaMZ depois de o serviço de hospedagem original (Railway) ter suspendido o backend e a base de dados por esgotamento de créditos. O objetivo era manter a aplicação pública sem custos, preservar a compatibilidade com MySQL, continuar a publicar automaticamente a partir do GitHub e não expor credenciais no código, no repositório ou na comunicação com o assistente.

Após comparar oito alternativas com base em documentação oficial, escolheu-se a combinação Render para o backend Node.js e TiDB Cloud Starter para a base de dados compatível com MySQL. A migração foi executada sem alterações ao código da API, criando a base e as tabelas por scripts próprios com ligação TLS, configurando seis variáveis de ambiente no painel da Render e actualizando uma única variável do repositório para o pacote Android.

O resultado foi verificado com sucesso: healthcheck com base online, doze categorias, doze serviços, login de demonstração com perfil de freelancer e um novo APK gerado automaticamente. O relatório documenta também dois incidentes reais, as suas correcções, os limites dos planos gratuitos e o trabalho futuro.

Palavras-chave: migração; hospedagem gratuita; Render; TiDB Cloud; MySQL; integração contínua; GitHub Actions; segurança de credenciais.

Nota sobre o histórico

O relatório original do projeto descreve a publicação no Railway e permanece no repositório como registo histórico. Este documento complementa-o com a fase posterior de migração.

Capítulo 1

1. Contexto e formulação do problema

O FreelaMZ é um marketplace que liga clientes a freelancers em Moçambique. A primeira publicação da API foi feita no Railway, com base MySQL gerida e deploy automático a partir do repositório GitHub. O sistema esteve operacional com o endpoint /api/health a reportar db:"up", doze categorias, nove freelancers e doze serviços de demonstração.

Em determinado momento, os créditos da conta foram esgotados. O painel passou a mostrar os serviços de backend e de base de dados com o estado Paused from exceeding limits, e a URL pública deixou de responder. A estimativa de regresso dos créditos era de aproximadamente vinte dias, prazo incompatível com a necessidade de manter a demonstração do projeto disponível.

Natureza do problema

A falha não era de código: o backend, o esquema da base e o pipeline do APK estavam funcionais. O risco identificado era a dependência de um único fornecedor com orçamento limitado e sem plano verdadeiramente permanente para este caso de uso.

Capítulo 2

2. Objetivos e critérios de decisão

A escolha da nova plataforma obedeceu a seis critérios, todos verificáveis em documentação oficial:

  1. Custo zero sustentável — plano gratuito sem cartão internacional e sem validade de trinta dias.
  2. Compatibilidade com MySQL — o projeto usa o driver mysql2, colunas JSON, ENUM, chaves estrangeiras e information_schema.
  3. Deploy automático por GitHub — ligação nativa ao repositório, sem copiar ficheiros manualmente.
  4. Segurança das credenciais — senhas e tokens introduzidos apenas nos painéis dos serviços, nunca no chat, no repositório ou no código.
  5. Comportamento previsível da quota — saber o que acontece quando o limite gratuito é atingido.
  6. Baixa manutenção — TLS gerido, healthcheck e reinício automático do serviço.

Ficou também definido que o projeto antigo só seria desligado depois de a nova instalação estar integralmente validada, de forma a permitir recuar em caso de falha.

Capítulo 4

4. Solução adotada e arquitetura

Foi escolhida a combinação Render + TiDB Cloud Starter. A Render oferece o deploy contínuo nativo por GitHub e aceita o comando de arranque já existente; o TiDB mantém a compatibilidade com o código de acesso à base e disponibiliza uma quota mensal explícita que, quando esgotada, estrangula a instância até ao mês seguinte sem gerar cobrança.

Um aspecto determinante foi o facto de o código já estar preparado para ambientes diferentes: o módulo dbConfig.js aceita uma única MYSQL_URL, o servidor lê PORT e escuta em 0,0,0,0, o CORS é configurável por CORS_ORIGINS e o seed de demonstração é controlado por SEED_DEMO. Por isso, nenhuma linha da lógica de negócio precisou de mudar para a migração.

Decisão sobre os dados antigos

Confirmou-se que não existiam dados reais no Railway além do catálogo de demonstração. A exportação do dump foi portanto dispensada: o Railway não precisou de ser reactivado e a base nova foi povoada pelo mecanismo de seed já implementado.

Capítulo 5

5. Execução da migração

5.1 Criação da base sem SQL Editor

A consola do TiDB Cloud Starter disponibilizada não mostrava o SQL Editor. Em alternativa, foi criado o script backend/scripts/criar-base-tidb.js, que liga com mysql2 e ssl: {} ao gateway da região São Paulo, executa CREATE DATABASE IF NOT EXISTS freelamz com utf8mb4_unicode_ci e termina com SHOW DATABASES. A senha é lida exclusivamente da variável TIDB_PASSWORD no ficheiro local backend/.env.

5.2 Criação das tabelas

Verificou-se que o seed automático pressupõe a existência das tabelas. Foi então criado o script backend/scripts/preparar-tabelas-tidb.js, que aplica, por ordem, database/schema.sql, database/seed.sql e src/scripts/migrate.js. O resultado foi de quinze tabelas, doze categorias e todas as migrações da chamada FASE A (carteiras, transações, escrow, entregas e levantamentos).

5.3 Configuração da Render

Foi criado um Web Service ligado ao repositório, com Root Directory backend, comando de compilação npm install, arranque npm start, plano Free e healthcheck em /api/health. As variáveis de ambiente foram introduzidas no painel através do botão Add from .env, usando um modelo limpo com apenas as seis variáveis necessárias.

5.4 Actualização do cliente e do APK

O frontend de desenvolvimento permaneceu com VITE_API_URL=/api, mantendo o proxy do Vite para o servidor local. Para o APK, bastou alterar a variável de repositório VITE_API_URL no GitHub para https://freelamz.onrender.com/api e disparar o workflow build-apk.yml. Nem o workflow nem o ficheiro capacitor.config.js precisaram de alterações, porque ambos já liam essa variável.

Capítulo 6

6. Incidentes e correções

6.1 Utilizador não preenchido

O primeiro arranque na Render reportou db:"down". O endpoint de diagnóstico devolveu ER_UNKNOWN_ERROR: Missing user name prefix e mostrou o utilizador como <UTILIZADOR_TIDB>. O marcador do ficheiro de exemplo tinha sido colado literalmente na MYSQL_URL. A correcção consistiu em substituí-lo pelo utilizador real no painel da Render, mantendo o sufixo .root exigido pelo TiDB. A senha nunca apareceu no diagnóstico.

6.2 Tabelas ausentes

Com a ligação corrigida, o healthcheck passou a mostrar db:"up", mas o seed terminou com ER_NO_SUCH_TABLE: freelamz.categories. Isto aconteceu porque a base nova estava vazia e o código de demonstração assume o esquema já aplicado. A execução do script de tabelas descrito em 5.2 resolveu o problema sem necessidade de novo deploy: o servidor revalida a ligação e volta a tentar o seed a cada sessenta segundos.

Diagnóstico útil

O endpoint /api/health/db revela host, porta, base e estado da ligação, mas não a senha. Foi decisivo para distinguir um erro de configuração de um erro de estrutura da base.

Capítulo 8

8. Segurança e gestão de segredos

Uma regra explícita orientou toda a migração: nenhuma senha, token de acesso, JWT_SECRET ou string de ligação com senha seria pedida ou partilhada na conversa. Na prática:

  • A senha do TiDB foi escrita pelo próprio utilizador no ficheiro local backend/.env, que está ignorado pelo Git.
  • Os scripts de criação da base e das tabelas leem essa variável do ambiente e nunca a imprimem; os erros são filtrados.
  • As variáveis de produção foram introduzidas directamente no painel da Render, incluindo o JWT_SECRET gerado localmente.
  • A actualização da variável do GitHub e o disparo do workflow foram feitos com a autenticação já existente da ferramenta de linha de comando, sem colar tokens.
  • O modelo .env.render.example contém apenas marcadores, nunca valores reais.
Resultado

Nenhum segredo foi encontrado no repositório, nos ficheiros de documentação, nos logs apresentados ou na comunicação durante a migração.

Capítulo 9

9. Limitações e trabalho futuro

Os planos gratuitos envolvem compromissos que devem ser conhecidos. A Render adormece após quinze minutos inactiva e o primeiro pedido pode demorar cerca de um minuto; além disso, esgotando as 750 horas mensais ou a banda incluída, os serviços gratuitos são suspensos. No TiDB, o esgotamento dos cinquenta milhões de unidades de pedido estrangula a instância até ao mês seguinte.

O sistema de ficheiros da Render é efémero: imagens enviadas para a pasta de uploads desaparecem a cada deploy. Para um produto real seria necessário armazenamento externo compatível com S3. A publicação na Play Store também continua pendente, pois o APK actual é de depuração e ainda não foi assinado com uma chave própria.

Como trabalho futuro imediato ficaram definidos:

  1. Desligar o projeto antigo no Railway após a validação, hoje concluída.
  2. Criar uma chave de assinatura e gerar um APK de lançamento.
  3. Introduzir armazenamento externo para ficheiros enviados.
  4. Acompanhar o consumo da quota do TiDB e da Render ao longo do mês.

Capítulo 10

10. Conclusão

A migração atingiu todos os objectivos fixados no início: a aplicação voltou a estar pública sem custo, a compatibilidade com MySQL foi mantida, o deploy automático por GitHub continuou a funcionar e nenhuma credencial foi exposta. O processo também mostrou que uma preparação prévia adequada — variáveis de ambiente, healthchecks e scripts idempotentes — permite trocar de fornecedor sem reescrever a aplicação.

Os dois incidentes encontrados não estavam no código, mas na configuração e na ordem das operações. Foram resolvidos com diagnóstico baseado em evidências e registados neste documento para que uma futura migração possa ser executada de forma ainda mais directa.
